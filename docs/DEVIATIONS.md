# Deviations from the pre-registered design

Every change to the frozen design (pre-registration v1, 18 Nov 2026) is recorded here before it is applied.
Changes made after seeing any data are marked **post-hoc** and reported as such in the paper.

| Date | Section of design | What changed | Why | Before or after data? |
| --- | --- | --- | --- | --- |
| 2026-11-18 | Section 5 (Arm A), Sections 8, 10, 11 | Consensus for Arm A changed from IBFT 2.0 to QBFT (still Hyperledger Besu, 4 validators, block period 2 s) | Besu documentation recommends QBFT for new private networks; IBFT 2.0 is supported only for existing networks. Both are BFT with immediate finality and need at least 4 validators, so the comparison with Arm B is unchanged | Before any data (no runs yet); not post-hoc |
| 2026-11-19 | Section 8 (F2, F3, F4) | Clarification, not a change of criteria: how the pass criteria are measured. F2 "alert raised" = no centre obtained the key by T0 + 60 s (TIMEOUT_MS = 60000) and fewer than k shares were accepted (recorded as `alert: "insufficient shares"`); "no partial key exposed" = no centre obtained any key (with fewer than k shares the clients do not attempt reconstruction). F3: the first present trustee submits its share with one byte flipped at T0 (validly signed in B), before the honest submissions; rejected = HTTP 422 in B, mined transaction reverted with no share stored in A. F4: the first present trustee submits once at T0 - 5 s; rejected = HTTP 425 in B, transaction mined in a block with timestamp < T0 and reverted in A. In A both fault transactions use a fixed gas limit so that the contract, not the client's gas estimate, rejects them | The design states the criteria but not their measurement; fixing them in code (`harness/scripts/check-faults.js`) before running avoids choosing a definition after seeing results | Before any fault-test data |
| 2026-11-20 | Sections 5 and 8 (Arm A clients; F6, F7) | (1) Arm A centres now get all 4 validator RPC endpoints, own node first, and fail over in order (before: own node only). (2) Arm A RPC requests time out after 2 s (`RPC_TIMEOUT_MS`, before: ethers default 300 s), the same per-request timeout Arm B's etcd client already used. (3) Measurement of F6: 5 of 50 centres (0, 10, 20, 30, 40) are censored; in B the coordinator refuses them (HTTP 403); in A their own node refuses them (unreachable endpoint) and they may read from the other validators; pass = every censored centre gets the correct key within T0 + 60 s. F7: `docker kill` of etr-besu4 (A) or etr-etcd3 (B) at T0 of the measured session; pass = kill confirmed within 1 s after T0 and every centre gets the correct key. In A trustee 3 uses the killed node, so 4 of 5 shares remain (k = 3) | The design says centres read the chain directly and that one replica may crash; with a single endpoint and a 300 s timeout an A centre would fail because of client configuration, not the ledger. With all nodes up the new client behaves exactly as before (the own node answers first), so the group 1 fault results (F1-F4, commit 0ea62ce, single endpoint) are unaffected | Before any F6/F7 data and before the main runs; after the group 1 fault tests (which do not exercise these paths) |
| 2026-11-20 | Sections 7 and 8 (load generator, sampler, F6/F7 measurement) | After the group 3 smoke check: (1) Arm A clients in the load generator use the validators' fixed IPs (172.28.0.11-14) instead of container names; (2) the F6 censoring endpoint in A is a closed local port (refuses at once) instead of an unresolvable host name; (3) CPU-seconds = max minus first sample of the cumulative counter (equal to last minus first unless a container is killed); (4) F7 timing criterion uses the time the kill command was issued (within 1 s after T0), not the time `docker kill` returned | Smoke runs showed DNS look-ups for a killed or invalid name slowing every centre in the shared load generator (harness artefact, not ledger behaviour), a negative CPU value for the killed container, and `docker kill` taking about 0.7 s to return. With all nodes up, (1)-(3) give the same behaviour and numbers as before, so group 1 results (F1-F4) are unaffected | Before any F6/F7 data and before the main runs (smoke only) |
